# Kado 機能過不足トリアージ

> 対象読者: このドキュメントは Kado プロジェクトの文脈を持たない別セッション
> (Opus・Sonnet 等、モデルを問わず) が読んでも単独で理解できるように書く。
> 本文中の「問NNN」は `docs/socratic-review.md` の該当エントリへの参照
> (追跡用の注記であり、読むために遡って参照する必要はない)。
> 最終更新: 問282 (v148) 時点。

## 0. Kado とは何か (最小限の前提)

Kado は AI エージェントが3D形状を生成・検証・製造用ファイルに出力するための
ローカル完結ジオメトリエンジン (Rust, std のみ, 外部送信ゼロ, 決定的出力)。
中核は **SDF (符号付き距離場)**: プリミティブと変換をJSON/テキストDSL
(`KadoScene`) で組み立て、`Marching Tetrahedra` で水密メッシュに変換し、
STL/GLB/3MF/HTML/PNG を出力する。AIエージェントは **MCPサーバー** (stdio,
JSON-RPC 2.0) 経由でこれを呼び出す。詳細仕様は `docs/SPEC.md`、設計判断の
根拠は `docs/adr/ADR-001〜003`、逐次の問答記録は `docs/socratic-review.md`。

## 1. トリアージの判断軸

「機能が多すぎないか (過剰)」「足りない機能はないか (不足)」を継続的に
監査する。判断は次の2軸のみで行う:

- **(a) 代替可能性**: その機能がなくても、既存の仕組み (演算子の組み合わせ・
  AIの会話コンテキスト・逐次呼び出し) で同じ効果を得られるか。得られるなら
  追加不要 (過剰候補)。
- **(b) 規律適合性**: 追加がプロジェクトの規律 (レスポンスサイズ上限・
  恣意的な閾値を導入しない・決定性・std-only 依存ゼロ) を破らないか。
  破るなら見送り。

## 3. 不足と判定し実装済みの機能

過去のレビューで「欠けている」と判定し、実際に追加した機能:

| 機能 | 追加理由 (なぜ既存機能で代替できなかったか) |
|------|------|
| `rotate(ax,ay,az,angle)` — 任意軸回転 | オイラー角 (rotate_x/y/z の合成) での代替は理論上可能だが、AIエージェントが実務上つまずく変換の障壁だった。Rodrigues の回転公式で直接実装 (問266) |
| `projection=orthographic` — 正射影screenshot | 「多面図」「等角図」という名前が本来意味する図法と、Kadoの既定 (透視投影) が食い違っていた。寸法比を目視で正しく判断するには必須 (問267) |
| `prism(n,r,h)` — 正多角形プリズム | CADの基本操作。正多角形限定なら閉形式のSDFが文献上既知 (IQ の `sdRegularPolygon`) だったため実装可能と判定 (問269) |
| `scale_xyz(sx,sy,sz)` — 非一様スケール | 当初「距離場の性質を壊す」という理由で見送っていたが、この前提が数学的に不正確だと判明。符号厳密性・保守的過小評価・Lipschitz=1 を証明した上で実装 (問276) |
| PNG screenshot の実圧縮 (決定的DEFLATE) | 応答サイズ削減の効果が大きいが、std-only での実装は複雑という理由で先送りしていた。Kadoの実ワークロード (単色背景・平坦面) に絞ったRLE+固定Huffmanなら規律の範囲内で実装可能と判明。無圧縮 stored との `min()` を取るため既存動作からの退行なし。実測で無圧縮比8.3%まで縮小 (問281) |

## 4. 過剰候補として検討し却下した機能 (追加しない)

| 候補 | 却下理由 |
|------|------|
| 一括複数視点 screenshot (7視点まとめて1回で返す) | 無圧縮PNGなら1024²で787KB実測×7視点=数MB応答になり、MCPのレスポンスサイズ規律に反する。逐次7回呼び出しで同じ結果を得られる (代替可能性)。※問281でPNG実圧縮を導入し512²でraw比8.3%まで縮小したため、この試算の前提は変わった。却下自体は撤回していないが、再検討の余地はありユーザー判断待ち |
| 多段 undo スタック | 正本はスクリプト (DSLソース) であり、AIが過去のスクリプトを再送すれば同じ効果を得られる。サーバー側に状態を追加する必要がない |
| 三角形数過多への DFM 警告 | 製造可能性そのものの欠陥ではなく性能上の懸念に過ぎず、警告の閾値が恣意的になってしまう |
| STL/GLB 書き出しの u32 オーバーフローガード | 解像度上限 (`MAX_RESOLUTION=256`) の制約下では到達不可能な頂点数であり、起こり得ないシナリオへの過剰防御になる |
| `repeat` のネストによる指数爆発への対策 | 実際には誤報だったと判明。SDF評価はネストのレベルごとにO(1)であり、既存の深さ上限 (`MAX_DEPTH=64`) がすでに線形にしか増えないことを保証している |

## 5. 残っている不足候補 (未実装)

| 候補 | 現状評価 |
|------|------|
| ねじ/ヘリカル形状 (thread / helix) | 調査の結果、当面見送り。理由は下記5.1を参照。専用プリミティブなしでも `repeat` 等の既存演算子による近似は可能 (問270) |
| メッシュインポート (STL読み込み) | **【問296 で解決・実装済み】** 保守的な**検証専用**設計を採用: `validate-stl` CLI コマンドで外部 binary STL を読み込み DFM 検証するが、SDF シーン正本には決してしない (ADR-001「SDF が唯一の正本」を保存)。mesh→SDF 再構成は行わない (数値破綻回避)。読み取り攻撃面を増やさないため MCP には出さず CLI 専用。SDF として再編集する用途は引き続き非目標。 |
| MCP 2026-07-28 リリース候補 (RC) への対応 | **watch 項目**。安定版 2025-11-25 には対応済み (問286)。次版は現在 RC のため採用は見送り。GA 昇格時に版交渉リストへの追加を再検討する ([RC 告知](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)) |

### 5.1 ねじ/ヘリカルを見送った理由 (問270 の詳細)

一般的な「角度をアンラップする」手法 (θ=atan2(y,x), h'=z-pitch·θ/(2π) として
周期パターンを h' に適用する) は、Kado の既存 `repeat` (デカルト軸に沿った
スナップ、Lipschitz=1 の証明が容易) とは根本的に異なる**角度ベースの
ドメイン変形**になる。同じ角度差 Δθ が、回転軸からの距離 r に比例した弧長
r·Δθ に対応するため、軸から離れるほど歪みが増大し、**Lipschitz定数が半径に
依存して発散する** (単純な式で有界性を保証できない)。

厳密に「ヘリックス曲面上の最近傍点」を求める経路もあるが、これはヘリックスの
パラメトリック方程式に対する超越方程式になり、閉形式ではなく反復数値解法
(Newton法等) が必要になる。Kado の既存プリミティブ (楕円体を含め全て) は
単純な閉形式の f64 関数であり、反復解法は初めて導入する計算カテゴリになる
上、収束保証 (特にピッチが密なねじや回転軸付近) にも別途の安全策が必要で、
1ラウンドで実装・検証しきれる規模を超えると判断した。

## 6. 明示的に「非目標」として維持しているもの (`docs/SPEC.md` §9 と一致)

- クロスプラットフォームでのビット完全一致 (同一アーキテクチャ内でのみ保証)
- 薄肉の完全検出 (探針の刻み幅より薄い壁は見落としうる。安全側の補助情報)
- 楕円体の軸外での厳密距離 (IQによる近似。符号と軸上距離のみ厳密)
- メッシュ同士のブーリアン演算 (数値破綻を避けるため、常にSDF経由のみ)
- 無限回の反復配列 (`repeat` は有限回のみ)

## 7. 総括

3巡のレビューを通じて「過剰」と判定して削除した機能は0件 (9ツール・
33演算子・11コードのすべてに独立した存在理由がある)。「不足」と判定して
実装した機能は8件 (任意軸rotate・正射影・prism・scale_xyz・PNG実圧縮・
面取りブーリアン chamfer_*・STLインポート検証専用・measure 光線測定)。
根拠付きで却下・見送りにした候補は6件。かつて唯一未解決だったメッシュ
インポートは問296 で検証専用 (`validate-stl`・SDF 正本にしない) として実装し、
現時点で未解決の候補はゼロ。

2つの対照的な教訓が残っている: ねじ/ヘリカル (問270) は「閉形式で
Lipschitz有界な厳密解が文献上存在しない」という数学的な限界により見送った
のに対し、scale_xyz (問276) と PNG圧縮 (問281) は逆に「実装できない」という
従来の判断理由そのものが不正確・過度に悲観的だったと判明し、規律の範囲まで
スコープを絞ることで実装に転じた。トリアージは一度の判定で終わらせず、
前提を定期的に疑い直す価値がある。
