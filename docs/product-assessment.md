# Kado プロダクト評価 — 長所・短所・改善点

> 対象読者: Kado の文脈を持たない読者。単独で読めるように書く。
> 「問NNN」は [`socratic-review.md`](socratic-review.md) の該当エントリへの参照。
> 本書は**主張ではなく状態**を記す。各項目には**それを強制しているテスト名**を添える——
> テスト名が無い行は「そうなっている」であって「そうであり続ける」ではない（問316）。
>
> 数値を手で同期しない（問324/329/334 で 4 回腐らせた）。本数・実測値は
> `cargo test --all-targets` と `./scripts/check.sh` が常に表示する。

## 0. Kado とは

AI エージェントが 3D 形状を**生成・検証・製造用出力**するためのローカル完結エンジン。
SDF 木を正本とし、Marching Tetrahedra で水密メッシュを抽出、DFM 検証して
STL/GLB/3MF/HTML/PNG を出力する。AI は MCP（stdio・JSON-RPC 2.0）で呼ぶ。
Rust std のみ・外部 crate ゼロ・ネットワーク I/O 無し。

## 1. 長所 — 契約になっているもの

「良い」ではなく**「壊すと落ちる」**ものだけを長所として数える。

| 性質 | 強制手段 |
|---|---|
| 外部送信ゼロ（ソケット不使用） | `no_source_file_references_network_apis` |
| 外部送信ゼロ（生成物経由） | `scripts/interop-check.py`（HTML の外部参照検査） |
| 外部依存ゼロ | `cargo tree` 検査（`scripts/check.sh` + `docs/ci.yml`） |
| 決定的出力（スレッド数非依存まで） | `parallel_extraction_is_bit_identical_regardless_of_thread_count` |
| 引数を黙って読み替えない | `no_production_code_silently_coerces_an_argument_to_a_default` |
| エラーが引数名を挙げる | `every_arity_error_names_its_parameters` |
| 著述ミスから回復できる | `recoverable_error_rate_over_realistic_authoring_mistakes` |
| issue code の宣言と実装の一致（双方向） | `every_emitted_issue_code_is_declared_and_vice_versa` |
| SPEC の上限表とソースの一致 | `spec_resource_limit_table_matches_the_source` |
| 改行コードの固定（Windows 対策） | `gitattributes_pins_line_endings_to_lf` |
| README の手順が実際に通る | `the_readme_quickstart_actually_runs_and_succeeds` |
| CHANGELOG が宣言した形式を保つ | `changelog_keeps_the_structure_it_claims_to_follow` |
| フレーム破損が正常終了と区別される | `framing_corruption_is_diagnosed_on_stderr_and_exits_nonzero` |
| 品質ゲートの自動実行 | `.githooks/pre-push`（`git config core.hooksPath .githooks`） |

### 測って確かめた性質（バグは無かった）

- **幾何精度**: 解析解と比較して sphere/cuboid/cylinder/torus すべて体積・面積とも
  **誤差 0.06% 以内**（問328）。
- **プリミティブの取り決め**: `cylinder` の `h` は半高、`cone` は全高で原点中心でない。
  紛らわしいが**文書・実装・テストが三つとも一致**している（`sdf.rs` の aabb テスト）。
- **リソース上限**: 深さ 200 のネスト・65,535 ノード・2.4MB ソースをいずれも終了コード 1 で
  拒否。クラッシュ・OOM・ハングなし（問330/335）。
- **外部相互運用性**: STL/3MF/GLB/HTML を独立実装でデコードして検証（問324）。
- **HTML ビューア**: headless Chromium で実描画を確認。WebGL2 非対応環境では
  白画面ではなく明示メッセージ（問328）。
- **死んだ公開 API**: **ゼロ**。`pub` 項目はすべて製品コードから使われている（問334）。

## 2. 短所 — 見つけて直したもの

すべて**実行して**見つかった。読むだけでは見つからなかった。

| 深刻度 | 欠陥 | 問 |
|---|---|---|
| **データ破壊** | `kado export scene.txt out.stl` が **scene.txt を STL で上書き**し、`out.stl` を無視し、中身はデモモデルだった | 321 |
| **偽装ファイル** | 未知拡張子が黙って STL に。`a.xyz` は `a.stl` と**バイト単位で同一** | 322 |
| **誤った合格** | `build_dir:[0,0,0]` がオーバーハング検査を丸ごとスキップし、AI が「指摘なし」を合格と読む | 318 |
| **起動時 panic** | CRLF チェックアウトで Windows CI が最初のテストで落ちる（`.gitattributes` 不在） | 317 |
| 無防備な主張 | 「外部送信ゼロ」だけ強制手段が無かった（`cargo tree` は `std::net` を検出できない） | 316 |
| 初回体験 | **README クイックスタートの最後が終了コード 1**（2mm の球に 0.8mm 肉厚を課していた） | 332 |
| 無言の失敗 | フレーム破損が**正常終了と区別できない**（診断を作って捨てていた） | 335 |
| 誤誘導 | 深さ超過エラーが **1210 文字**（うち情報は末尾 3 文字、65 段の無意味なパス） | 330 |
| 測定の偽装 | 看板 KPI「無人完走率」が**著述を人間が肩代わりした状態**を測っていた | 331 |

### 繰り返した構造的欠陥

**同じ規律が片方の入口にだけ適用されている** — これが**5 回**繰り返した最大のパターン。

| 問 | 直っていた側 | 漏れていた側 |
|---|---|---|
| 318 | `view`/`projection`（問71/267） | `build_dir`・数値引数 |
| 325 | MCP の整数（問318） | CLI の整数 |
| 326 | CLI の閾値（問47） | MCP の浮動小数・文字列・真偽値 |
| 328 | MCP の解像度併記（問90/91/92） | CLI の `run`/`check` |
| 329 | README・SPEC 本文の本数（問324） | KPI 表の本数 |

問327 で構造的に禁止した（`no_production_code_silently_coerces_...`）。
**個別に直し続けても終わらない**——性質として表せば終わる。

## 3. 測っていないもの（測れると書かない）

- **AI がスクリプトを著述できるか**（問331）。評価セットは**人間が書いたスクリプト**を
  流している。著述の測定にはライブのモデルが要り、外部依存ゼロ・オフライン・決定的の
  制約と両立しない。代替として**回復可能率**を測っている。
- **SPEC 上限表の「値」列**（問334）。`1 MiB` と `1 << 20` の突き合わせには式評価器が要り、
  意図的にしか変わらない値には見合わない。網羅性と定義場所のみ機械検証。
- **Linux 以外の実行**（問317）。CI が未有効化のため未検証。CRLF 起因の既知欠陥は
  手元で再現して修正済みだが、**有効化されるまで「たぶん通る」以上のことは言えない**。

## 4. 改善点 — 未着手

### 4.1 リポジトリ管理者のみ実行可能

1. **CI の有効化**: `git mv docs/ci.yml .github/workflows/ci.yml`。
   Claude Code の GitHub App は `workflows` 権限を持たず、
   [`CLAUDE.md`](../CLAUDE.md) §6 も `.github/workflows/` への push を禁じている。
   問317 の修正により、有効化すれば Windows でも通るはず（未検証・上記 §3）。
2. **v0.2.0 のタグ付けとリリース**。

### 4.2 意図的に採らなかったもの（再提案の前に読むこと）

- **編集距離による「もしかして」提案**（問319）: 有効名を全列挙している以上 AI は既に
  正解を持っており、距離の閾値に根拠が無い（「恣意的閾値を持ち込まない」に反する）。
- **Windows のデバイス名・ADS・末尾ドットのフィルタ**（問317）: いずれも
  プロジェクト直下から脱出せず、サンドボックスの契約を破らない。脅威が特定できない
  段階で拒否ルールだけ増やさない。
- **`samples` × 寸法の上限超過をエラーにする**（問318）: 双方とも有効な値であり、
  積が上限に触れるのは物理制約にすぎない。**拒否するのは入力が誤っている場合だけ**。
- **負の閾値の拒否**（問326）: `verify/check.rs` が「0 以下でスキップ」を契約として
  文書化しており、`min_wall_mm: -1` は誤りではなく指示である。
- **4 巨大ファイルの分割**（`core/sdf.rs`・`verify/check.rs`・`mcp/tools.rs`・
  `script/eval.rs`）: テスト最厚であり、分割は決定性 churn の方が大きい。
- **DC（dual contouring）への置換**: 要求する具体的ユースケースが未発生（ADR-001）。
- **STL からの SDF 再構成**: 非目標。インポートは**検証専用**（ADR-001・問296）。

## 5. 本評価から得た方法論

1. **読むことでは見つからない欠陥がある。** 最も重い 3 件（問321/322/332）は
   すべて**製品を実際に動かして**見つかった。問322 に至っては
   **テストが「正しい」として固定していた**挙動だった。
2. **「テストが緑」は「使える」の証拠ではない。** テストは仕様を固定するが、
   仕様が正しいことは保証しない。
3. **測定の名前が範囲を偽ると、引用するたびに嘘が増える**（問331）。
4. **規律を 1 箇所に適用したことと、規律が行き渡ったことは別**（問327）。
   2 度同じ間違いをしたなら、それは不注意ではなく仕組みの欠落である。
5. **測定は結論の前に検算する。** 本評価の過程で自分の測定を 3 回壊した
   （GLB の改変位置・bash の語分割・`#[cfg(test)]` の切り出し）。
   検算しなければ「`call_tool` は未使用」と報告するところだった。
